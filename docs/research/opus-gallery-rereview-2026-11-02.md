## 見つけた問題と修正（`bacb221`）

### 1. ismcdnの `NNNw` レンディションを同一画像と認めない（悪化）

`photoIdentity` は `/mwimgs/` 内の `870m`・`1420wm` だけを正規化し、`680w`・`1360w`・`1200w`・原寸の `-` を残していた。`photoSource` は同一画像の候補内でしか高解像度を選ばないため、`680w` と `1360w 2x` が別画像になり小さい方が残る。

実HTMLでの確認（ローカル版関数を同じページに適用）:

| ページ | 修正前に選んだ画像 | 修正後 |
|---|---|---|
| TBS NEWS DIG 記事 `articles/-/3054376`（53枚） | 260w / 340w / 300w … | 520w / 680w / 600w …（各2x） |
| 東スポ 記事 `articles/-/408496` | 820w | 1640w |

人工HTMLでは、兄弟一覧のサムネイルが `120w`・大きい写真が `680w` の場合に一覧を認識しなくなる（旧photoStemでは認識）ことも確認。ページの代表画像 `1200w` と記事写真 `870m` も不一致になり、スライダーの「代表画像と一致」スコアが効かなかった。

修正: `/mwimgs/` 内の `\d{2,4}(?:wm|w|m)` と `-` のフォルダをすべて同一画像として扱う。ハッシュ部分は残すので別画像とは一致しない。

### 2. 遅延読み込みのダミーGIFを写真として返す（スライダーで悪化）

旧スライダーは候補からGIFを除いていたが、共通化した `photoSource` はSVG/ICOしか除かない。`src="1x1.gif"` で本物が `data-lazy-srcset` にしかないスライドで、ダミーGIFを写真として返していた（旧版はそのスライドを捨てていた）。

修正: `data-lazy-srcset` を候補に加え、`data-src` 等やsrcsetに名前がある場合は `src` のGIFを候補にしない。GIFしかない場合（アニメーションGIF）は従来どおり返す。

### 3. ギャラリーの証拠をページ全体のクラスから拾う

`galleryEvidence` がカルーセルの祖先を `html` まで遡るため、`<body class="single-photo-template">` のようなテンプレートのクラスで、記事ページの宣伝カルーセルも採用された（人工HTMLで3枚採用を確認）。

修正: カルーセル自身と直近4階層の親だけを見て、`main`・`body`・`html` に達したら止める。カルーセル自身のラッパーにある `article-gallery` 等は従来どおり証拠になる。

### その他

- `scripts/check-photo-pages.ts` の検証列（bad）が旧 `photoStem` で比較していたため、本番の `photoIdentity` に揃えた。

## 追記：文春オンラインの写真が小さい（`451f44c`）

利用者の報告（Yahoo記事 `465210bf…` → `bunshun.jp/articles/photo/93236?pn=2`）で確認。キャッシュではなく、次の2つが重なっていた。

2. 専用アダプタの失敗後、カルーセル判定がナビゲーション用のサムネイル帯（`#photo-thumbnail`、高さ64px）を写真一覧として採用した。空のサムネイル値がページURLに解決される不具合もあった。

- ARENA：APIが使えない場合だけ、ページ自身の `og:image`（表示中の写真の `1200wm` 版）が現在のサムネイルと同じ写真であることを確かめ、そのレンディションフォルダを全サムネイルに使う。APIが別画像を返した場合は従来どおりエラー。

教訓：専用アダプタが失敗した後に構造アダプタへ進む経路（PR #2の重点確認③）で、「写真として妥当な大きさか」を確かめていなかった。サムネイル帯の除外に加え、今後は採用した画像の宣言サイズ（幅・高さ・レンディション）が小さすぎる一覧を不完全扱いにする検査も検討してほしい。

## 追記：2回目の再レビューへの対応（2026-11-04）

6.1solの2回目の再レビュー（[PR #2のコメント](https://github.com/syoudai0514/ROMNOA/pull/2#issuecomment-6617366158)）の指摘をすべて直した。キャッシュはv34。

### 1. [P1] Impress Watchで別写真を表示する
- 原因：主画像 `#main-image` が次の写真ページ（`html/s3.jpg.html`）へのリンクに包まれており、汎用パーサーが「別文書へのリンクカード」として除外していた。
- 修正：同じオリジン・同じフォルダの写真ページ（`*.jpg.html` 等）どうしのリンクは、写真を包むリンクとして許可する。
- 実ページ：OG画像（別写真 s1）から、要求された s2（1200×1200）を選ぶようになった。

### 2. [P2] 操作用画像の除外が強すぎる
- 修正：alt が「前へ」「次へ」「閉じる」等の操作ラベルなら、その画像を除外する。ファイル名の icon/arrow/btn/button/sprite/nav だけでは除外しない。除外するには、さらに次のどれかを満たす必要がある。
  - 幅・高さの属性が100未満
  - サイト部品のフォルダ（`/common/`・`/assets/` 等）にある。ただし `/uploads/` などの記事画像フォルダは除く
  - 4階層以内に button、`role=button`、prev/next/nav/control 系のクラスがある
- `button-design.jpg`・`arrow-car.jpg` 等の本文写真4枚が残ることをテストで確認した。

### 3. [P2] WordPress原寸版の推測範囲が広すぎる
- フォルダ単位で一般化する処理を削除した。
- 代わりに `largestOnPage`（`server/photo-source.ts`）を全アダプタ共通で使う。ページ自身が書いているURL（img・`<picture><source>`・srcset・lazy属性・og:image・画像ファイルへのリンク）の中から、同じ写真の大きいレンディションだけを使う。推測したURLは使わない。
  - 大きさの比較：宣言サイズ、`large_`・`_b` の名前、`-WxH` 版と並ぶ無印（WordPressの原寸）、ismcdnの `-` の順で判断する。
  - `?width=` 型のCDNでは、無印URLを原寸とみなさない（mdprで確認）。
  - `sns_` は切り抜きの可能性があるため選ばない。
- デイリー新潮の実ページは、要求写真が 1200×800 になった。ページが原寸を書いていない写真は、ページにある最大版（714px等）か元の版のまま残る。

### 4. [P2] 文春APIの不一致エラーが隠れる
- `Promise.allSettled` で全応答を分類する。一件でも別画像の応答があれば `photo_mismatch` とし、OG代替は使わない。
- `photo_mismatch` は resolver で終端扱いにし、後段のアダプタで隠れないようにした。
- OG代替を使えるのは、og:image のホストが次のどちらかの場合だけにした。
  - サムネイルと同じCDN
  - ページ自身のホストで、サムネイルが `<サイト名>.ismcdn.jp` のとき（bunshun.jp → bunshun.ismcdn.jp）
- 他のARENAサイトは、この組み合わせが確認できない限り従来どおりエラーになる。

### 残る小画像
- **西日本新聞 `/image/N/`**
  - `<picture><source>` の `large_` 版（670px）を使う。
  - 位置指定のない写真ページでは、og:image と同じ写真のスライドから開く。
  - 実ページ：320px・別写真 → 670px・正しい開始写真になった。
  - 同一写真の判定には、数字のメディアフォルダ内の `small_`・`middle_`・`large_`・`sns_` 接頭辞を使う。
- **みんなの経済新聞**：ページにある `NNNN_b.jpg` を使う。実ページで、香港は330→1000px、金沢は330→1200px になった。
- **0115765.com**：原寸自体が280×280のため対象外。

### 大きさの検査
- `thumbnailEvidence` は判定を3つに分ける（小さい／十分／不明）。高さだけの指定（`?h=`・`400hm`）は長辺の証拠にしないが、120px未満なら小さいとみなす。

  - 表示中の写真が小さく、小さい写真が十分な大きさの写真以上にある
  - 小さい写真が全体の半分以上を占める

## 追記：原寸版の背景確認（`bee91d8`、2026-11-04）

6.1solの提案（[PR #2のコメント](https://github.com/syoudai0514/ROMNOA/pull/2#issuecomment-6619319462)）を採用した。

- **表示順**：今ある画像をすぐ表示する。表示し終えた後で、現在の写真、次の写真、前の写真の順に原寸版を確認する（`YahooPhotoFeature`）。拡大表示でも確認済みの原寸を使う。記事や一覧の取得処理では、追加の取得をしない。
- **候補**：確認済みの変換規則（WordPress の `name-WxH.ext` → `name.ext`）だけを使い、1画像につき候補は1件（`originalPhotoCandidate`）。
- **確認**：`/api/yahoo-photo-image?size=original` で、サーバーが候補を取得して確かめる（`confirmsOriginal`）。条件は次のすべて。
  - 画像として寸法が読める
  - 長辺が縮小版の宣言サイズの1.25倍以上
  - 縦横比の差が2%以内（同じ写真であることの確認。正方形の切り抜き等は除外）
- **失敗時**：404を返し、表示中の画像はそのまま。失敗した候補は1時間覚え、再取得しない。
- **キャッシュ**：確認済みの画像は他の画像と同じくキャッシュする（サーバー1時間、ブラウザ1時間）。
- **ブラウザ側**：画像を読み込み終えてから差し替える。空白や読み込み失敗の画像は表示しない。

実ページ（Vercel Sandbox hnd1）での確認結果：
- **デイリー新潮**：9枚のうち7枚を原寸（1200×800前後、14〜30万バイト、取得35〜56ms）に差し替えた。
  - `1516437_2-714x1071` の原寸は800×1200で、1.12倍しかないため差し替えなかった。
  - `1516437_1` はページ自身が原寸を書いているため、確認は不要だった。
- **0115765.com**：1024×767 → 2002×1500 になった。
