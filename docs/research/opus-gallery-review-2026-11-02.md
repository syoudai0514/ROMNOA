# Opusへの再レビュー依頼：写真一覧の帰属判定と画質選択

対象の土台は `78115b9`。構造アダプタ（兄弟一覧・カルーセル・縦型）の方針は維持し、境界条件を補強した。以下はモデル名への評価ではなく実装に対する引き継ぎコメント。

## 再現した問題と修正

1. **大きい別スライダーの誤採用**：記事の3枚と別枠5枚があると別枠を採用した。枚数の最大値ではなく、OG等の主画像一致と写真領域の明示を優先する。写真専用URLにある単独スライダーは従来どおり対応し、複数スライダーではその例外を使わない。
2. **同名画像の誤照合**：別フォルダの `image001.jpg` を同じ写真と判定した。新しい `photoIdentity` はオリジン・内容フォルダ・意味のあるクエリを保持し、既知のリサイズ部分だけ除く。IIDの `/imgs/p/<transform>/<mediaID>` と `/imgs/zoom/<mediaID>`、mwimgsのサイズフォルダ、WordPressの寸法接尾辞を正規化する。旧photoStemは調査スクリプト互換のため残し、本番の兄弟一覧・縦型判定は新しい識別子を使う。
3. **大きい不適合一覧が小さい正解を隠す**：現在写真のない4枚一覧があると正しい3枚一覧も捨てた。候補ごとに検証し、失敗時は次の一覧を試す。
4. **小さいlazy画像の優先**：data-src幅120とsrcset幅1600があっても幅120を選んだ。兄弟一覧とスライダーで共通のphotoSourceを使い、同一画像の候補内で大きい版を選ぶ。srcsetが別画像を指す場合は差し替えない。

APIの結果形式は維持。サーバーキャッシュはv28へ更新する。

## Opusに重点確認してほしい点

- 既知のCDN変換以外を保守的に扱うことで、実サイトの主画像とサムネイル照合に新たな取りこぼしがないか。特に別CDNへの移動は、ファイル名一致だけで許可する形へ戻さないでほしい。
- 複数の写真領域がともに明示的なgalleryクラスを持ち、OG画像がないページではまだ曖昧さが残る。カウンター・記事ID・本文への距離など、次に足す証拠の候補。
- スライダーの判定に落ちた後、genericへ進む経路も含めて誤混入を調べること。単一アダプタのnullだけで安全性を判断しない。
- srcsetのw/x・picture/source・クエリ式画像ID・同一画像の別フォーマットについて、実例ベースで拡張すること。今回のsource選択はimg属性が対象でpicture/sourceは追加対応の余地がある。
- 40/80枚の上限を単に増やすのではなく、総枚数・取得済み枚数・続き取得を共通化する設計。
- 次の品質評価は記事とHTMLを固定し、正解画像集合、混入率、画像単位の取得率、実画像ロード成功率、p95取得時間を分けて測る。
